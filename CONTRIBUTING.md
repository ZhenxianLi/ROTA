# Contributing

These rules apply to every change, including the author's own. They follow section 4 of [ROADMAP.md](ROADMAP.md).

## Independent implementation

ROTA's API is meant to be familiar to users of other numerical tools, but the implementation is independent.

Not allowed:

1. Reading, copying or translating the source code or internal data structures of any commercial software (numerical-computing toolboxes, commercial NVH analysis and simulation software). This includes opening built-in functions in an editor and stepping into them in a debugger.
2. Copying the text, example code or example data of commercial documentation. Docstrings, tutorials and examples are written from scratch.
3. Implementing or bundling a parser for a proprietary or unpublished file format, or describing its internal structure. Users convert their data to WAV, NPZ, HDF5 or CSV first.
4. Porting third-party code of unclear licence, including research code shared by colleagues or collaborators. Re-implement from the published paper and cite it.
5. Using trademarks of commercial products in the project name, package name or promotion.
6. Writing code comments of the form "reproduces function X of software Y". Write "implemented after <reference>" instead.
7. Using restricted data (partner vehicle recordings, participant data, unpublished datasets) as test fixtures or examples. The repository contains no vehicle models, partner names, participant information or absolute local paths.

Allowed:

1. Implementing algorithms from the published literature, with the source given in the References section of the docstring.
2. Using a commercial numerical environment as a black box: call public functions only, record inputs and outputs, and compare numbers.
3. Providing a factual correspondence table between ROTA functions and functions elsewhere.
4. Reusing open-source code under a licence compatible with GPL-3.0-or-later (e.g. BSD, MIT, Apache-2.0, GPL-3.0), acknowledged in a NOTICE file. Confirm the licence before reusing anything. Contributions are accepted under GPL-3.0-or-later.

## Code

- Dependencies: NumPy and SciPy only. Matplotlib is allowed only in `rota.plot` and in examples. Psychoacoustic toolboxes appear only as optional dependencies, in examples and, imported lazily inside functions, in `rota.bridges`.
- Every public function has a docstring with a References section. The docstring states the amplitude convention (peak or RMS) and the units of inputs and outputs.
- Units follow the README: s, Hz, rpm, revolutions, km/h. Signals have shape `(n,)` or `(n, ch)` and are processed per channel, linearly.
- Gains, calibration factors and reference pressures are explicit arguments, never built-in constants.
- Randomness takes a `numpy.random.Generator` or an integer seed.

## Tests

- Every public function is tested against analytic ground truth generated by `rota.synth`. Test and example data come only from `rota.synth`.
- Do not validate an estimator with the exact quantities that were used to generate its input and nothing else. Include speed errors, low-speed starts and other conditions where the answer is not trivially recoverable.
- Run `pytest -q` before opening a pull request. The same command runs in continuous integration on Python 3.10 to 3.13.

## Pull requests and commits

- Fill in the pull request template, including the independence confirmation.
- Commit messages are plain and factual.
- Update `CHANGELOG.md`.

## Before a release or any push of history

Search the full git history (for example with `git log -p`) for sensitive terms: names of commercial software, partner organisations, vehicle models, personal names, and absolute local paths. The term list is kept by the maintainer and is not stored in the repository. Remove or rewrite any hit before publishing.

## Releasing

Releases are made by the maintainer and published by continuous integration (`.github/workflows/publish.yml`):

1. Set `__version__` in `src/rota/__init__.py` to `X.Y.Z` and `version` and `date-released` in `CITATION.cff`.
2. Add the section `## [X.Y.Z] - YYYY-MM-DD` to `CHANGELOG.md`, with its compare link at the end of the file. This section becomes the release notes. Optionally add `.github/release-highlights/X.Y.Z.md` (a short tour with figures, image links pinned to the tag `vX.Y.Z`); it is placed before the CHANGELOG section.
3. Push to `main` a commit whose message starts with the line `Release X.Y.Z`, exactly, as the last commit of the push. Do not push the tag yourself.

The workflow then runs the tests, builds the distributions, uploads them to PyPI (trusted publishing, no stored token), tags the commit `vX.Y.Z` and creates the GitHub release. It does nothing for other commits (a first line that looks like a release but does not match exactly only gives a warning), and stops if the version or the changelog section do not match; if the tag exists already, nothing is published. A failed run can be re-run: files already on PyPI are skipped. Do not start any other commit message with `Release X.Y.Z`. Publishing a GitHub release by hand with the tag `vX.Y.Z` also uploads to PyPI. Running the workflow by hand with `notes_for = X.Y.Z` rewrites the notes of the existing release `vX.Y.Z` from the current `main` (nothing is built or uploaded).
